# 无人机 VIO、LIO 与 PX4 状态估计的分层关系

- 当前成熟度：L0 想法
- 来源：用户提供的 ChatGPT 对话“VIO LIO融合IMU”“解析无人机定位方案对比”
- 记录日期：2026-09-09
- 适用范围：使用 PX4 与伴随计算机的无人机自主定位系统

## 要解决的问题

相机、激光雷达、惯性测量单元（IMU）、视觉惯性里程计（VIO）、激光惯性里程计（LIO）和 PX4 EKF2 都会输出或处理“状态”，容易被混成一个模块。工程设计首先要明确各层负责什么、交换什么，以及哪一层承担飞行安全责任。

## 基本概念

- 传感器产生图像、点云、角速度、比力等原始测量。
- VIO 和 LIO 利用环境观测与 IMU 估计连续运动，输出局部位姿、速度及不确定度。
- Odometry（里程计）是相对于指定参考系的连续运动估计，不天然等于全局绝对位置。
- PX4 EKF2 使用飞控 IMU 做高频传播，并融合卫星定位、气压计、磁力计、光流或外部里程计等观测，形成飞行控制使用的状态。
- 控制器根据估计状态与目标之间的误差计算执行量；VIO 或 LIO 本身不直接等于飞行控制。

## 推荐分层

```text
环境
  ↓
Camera / LiDAR / 外部定位设施
  ↓
VIO / LIO / 外部目标跟踪
  ↓
带时间戳、坐标系、不确定度和健康状态的定位观测
  ↓
PX4 EKF2 等飞行状态估计器
  ↓
位置、速度、姿态
  ↓
规划与控制
  ↓
执行器
```

这种分层允许替换定位来源，同时把高频姿态估计、控制和失效处置保留在飞控侧。

## IMU 的职责分配

一个系统可能同时有多颗 IMU：

```text
飞控 IMU ─────────────→ PX4 EKF2

视觉域 IMU + Camera ─→ VIO ─┐
                              ├→ 外部里程计观测 → PX4 EKF2
雷达域 IMU + LiDAR ───→ LIO ─┘
```

让每个定位子系统优先使用与其主传感器具有明确时间关系的 IMU，可以减少跨设备时钟、长通信链路和外参不确定性。飞控仍使用自己的 IMU 保持高频、安全关键的本地传播。

这不是必须遵守的硬规则。VIO 可以使用独立 IMU，也可以使用飞控 IMU，但后一种方式需要处理相机与飞控之间的时间同步、空间外参、传输抖动和数据相关性。

## 外部里程计接口至少应表达什么

- 测量时间戳，而不是只有消息到达时间；
- 位姿、速度分别在哪个坐标系中表达；
- 父坐标系、子坐标系和坐标轴约定；
- 位姿和速度的协方差或其他不确定度；
- 数据序号、有效状态和质量指标；
- 估计器重置或重新定位计数；
- 当前处理延迟或时间同步状态；
- 观测冻结、跳变、乱序和超时状态。

接口名称相同不代表语义相同。ROS 2 `nav_msgs/Odometry`、MAVLink `ODOMETRY` 与 PX4 内部消息之间的坐标系、时间戳和协方差语义需要按具体版本核对。

## 多定位源不是简单叠加

VIO、LIO 和外部定位可以作为候选观测源，但同时输入不自动等于更可靠。必须回答：

- 它们是否使用了相同的原始测量？
- 误差是否相关？
- 坐标原点和航向是否一致？
- 某个估计器重启时是否发生跳变？
- 协方差是否经过校准，还是固定填写？
- 谁负责选择、融合、降权和隔离故障源？

如果 VIO 使用飞控同一颗 IMU，随后又把 VIO 结果送回使用该 IMU 的 EKF2，可能形成相关观测或重复利用信息。是否造成过度自信取决于估计器结构和噪声建模，不能把 VIO 输出默认视为独立测量。

## 典型失效方式

| 失效 | 可能表现 | 需要检查 |
| --- | --- | --- |
| 时间戳语义错误 | 快速运动时残差和漂移增大 | 采样时刻、曝光时刻、到达时刻 |
| 坐标系错误 | 方向颠倒、转弯发散、位置突跳 | ENU/NED、机体系、传感器系 |
| 协方差失真 | EKF2 过度相信或拒绝观测 | 残差统计和实际误差 |
| 估计器重置 | 轨迹原点或航向突然变化 | 重置计数和连续性处理 |
| 数据冻结 | 数值不变但消息仍在发送 | 序号、时间戳和变化率 |
| 观测相关性被忽略 | 状态不确定度虚假缩小 | 原始测量来源和融合拓扑 |
| 多源身份或模式混乱 | 错源接管或频繁切换 | 健康管理和状态机 |

## 最小验证顺序

1. 只验证单一定位源的离线轨迹和时间戳。
2. 明确所有坐标系、变换方向和单位。
3. 在静止、平移、旋转和组合运动下检查输出连续性。
4. 将外部里程计接入 PX4，但先不闭环飞行，检查创新量、拒绝状态和延迟补偿。
5. 从系留或低风险悬停开始验证闭环。
6. 注入延迟、丢包、冻结、重置和坐标跳变，验证拒绝与降级。
7. 单源稳定后再考虑多源切换或融合。
